# 协议扫描项目面试复盘：持久化、一致性与并发调度

## 1. 先给结论（30 秒版本）

- 这个项目是高并发、乱序完成的流水线系统。
- 在崩溃恢复场景里，优先级应当是：不缺漏 > 严格不重复。
- 工程上选择了至少一次（at-least-once）语义：允许少量重复，避免漏扫。
- 关键机制是“按序号连续前缀提交（commit frontier）”：只推进连续完成区间，不用“最大完成序号”推进。

## 2. 面试官质疑点与标准回答

### Q1：极端情况下要保证不缺漏，是否必然会有重复？

可回答：

“在非事务化的文件持久化里，通常是的。因为结果落盘与进度推进之间存在崩溃窗口。若先写进度后写结果会缺漏；先写结果后写进度最多重复。为避免缺漏，我们有意选择后者，语义是至少一次。”

补充要点：

- 不缺漏与严格不重复同时 100% 保证，需要更强事务机制。
- 扫描系统强调吞吐与鲁棒性，优先不缺漏是更合理的工程权衡。

### Q2：为什么不直接用“本批最大完成序号”更新进度？

可回答：

“最大序号会跨过中间空洞，重启后容易漏扫。正确做法是只提交连续前缀：维护 next_commit_seq，从它开始向后检查是否连续完成，遇到空洞就停，绝不跳过。”

### Q3：严格不重复是不是代价很大？

可回答：

“是。严格不重复要求结果写入与进度推进处于同一原子事务域（例如事务数据库或 WAL + 原子提交协议），这会增加实现复杂度、I/O 开销、运维成本和时延。扫描场景通常采用至少一次 + 去重策略，更具性价比。”

### Q4：为什么一个 session 只负责一个 target，批量会不会更好？

可回答：

“单 target session 的核心优势是失败隔离、超时控制和恢复语义清晰。批量 session 在对象管理上可能有小收益，但会显著增加状态机复杂度（部分成功/部分超时/部分取消），恢复和重试也更难解释。”

补充对比：

- 单 target session：
  - 优点：隔离好、可观测、checkpoint 语义清晰、错误边界明确。
  - 缺点：对象数量更多、调度频率更高。
- 批量 session：
  - 优点：潜在更低调度开销。
  - 缺点：大幅提高状态与恢复复杂度，尾延迟和局部故障影响更大。

## 3. 本项目当前方案（深入）

### 3.1 数据模型

每个 target 增加：

- seq：输入序号（全局单调递增）
- source_offset：输入文件字节偏移（行起始）
- offset_ordinal：同一 offset 下第几个展开目标（用于 CIDR/范围行内恢复）

checkpoint 记录：

- processed_count：已连续提交数量（即前缀边界）
- successful_count：成功数统计
- input_file_hash：输入文件指纹
- input_file_offset + input_offset_ordinal：恢复起点

### 3.2 提交流程

result 线程对每批数据执行：

1. 先入 pending（seq -> report）
2. 从 next_commit_seq 开始检查连续可提交
3. 对连续段执行：
   - 先写结果文件
   - 再更新 checkpoint
4. 遇到空洞立即停止推进

这避免了“慢 IP 未完成但被快 IP 跨过”的漏扫问题。

### 3.3 为什么不需要排序

- 每批只做哈希插入与连续探测。
- 复杂度接近 O(batch)。
- 不依赖批内顺序，也不要求批次之间连续。

### 3.4 崩溃语义

- 最坏情况：结果已写、checkpoint 未推进 -> 重启后重复一小段。
- 不会出现：checkpoint 已推进、结果未写 -> 漏扫。

## 4. 边界与风险控制

### 4.1 pending 内存会不会爆

在有并发上限和超时上限时，pending 通常受在飞任务窗口约束，不会无限增长。

可解释方式：

pending 规模 ~= 已完成但被前序空洞阻塞的任务数 <= 在飞窗口上限 + 少量队列缓冲

### 4.2 慢任务阻塞前沿

是可能的，但每个协议探测有最大超时，最终会返回失败终态并填洞。可继续加背压阈值防止瞬时堆积。

### 4.3 输入文件变更

恢复前校验 input_file_hash。不一致时拒绝旧 checkpoint，避免错位恢复。

## 5. 你在面试中可主动说的改进路线图

### Phase 1（已做）

- 序号化 target
- 连续前缀提交
- 先结果后进度
- 输入 hash 校验

### Phase 2（可提）

- completion WAL（完成事件日志）
- 崩溃后重放恢复 pending/frontier
- 去重键（target, protocol, port, run_id）

### Phase 3（高成本可选）

- 事务型存储统一承载结果与进度
- 追求接近精确一次语义

## 6. 高频追问模板（可直接背）

### 模板 A：承认问题并给工程化修复

“当时方案的确有按最大完成位置推进的风险，后来我把它改成了按连续前缀推进。核心是 target 序号化、pending 缓冲、next_commit_seq 提交，保证崩溃时不缺漏，最多重复一段。”

### 模板 B：解释权衡

“这个系统的目标是大规模并发扫描，优先级是正确性中的不缺漏和可恢复。严格不重复是可选增强，但需要事务化一致性，代价显著高于当前收益。”

### 模板 C：回答 session 粒度

“我选择一目标一会话，主要是故障隔离和恢复语义清晰。批量会话可能降低少量调度开销，但会明显提高状态管理复杂度和恢复难度，在当前阶段不划算。”

## 7. 一段 60 秒自我复盘陈述

“这个项目最初的断点恢复有一个典型并发系统问题：结果乱序完成时，如果按‘最大完成位置’推进，会有漏扫风险。后来我做了三件事：第一，给每个输入目标加全局序号；第二，在结果线程维护 pending 和 next_commit_seq，只提交连续前缀；第三，严格执行先写结果后写进度。这样在故障场景下最多重复不会缺漏。关于面试官问的 session 粒度，我的判断是一目标一会话更利于故障隔离和可观测，适合当前高并发扫描业务，后续再视瓶颈评估批量化收益。”
